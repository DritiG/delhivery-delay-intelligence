# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, AI & ML Certification Program, E&ICT Academy, IIT Roorkee.

This project answers three questions for the regional operations head:
1. How long will a parcel take to deliver?
2. Which parcels will miss their promised delivery time?
3. Which hubs need which playbook?

All data is synthetic (made by `generate_data.py`). Real Delhivery data is not used. Every number below comes from a file in `outputs/` or `models/`.

## How to run

Python 3.11 or newer is needed. From a fresh clone, run these commands in this order:

```bash
pip install -r requirements.txt
python generate_data.py
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

`generate_data.py` prints `24 1224 48`. `requirements.txt` pins pandas, numpy, scikit-learn and joblib with `==`. The file `models/delay_model.pkl` is regenerated by running `python package_model.py`. The saved pickle loads reliably only on the scikit-learn version pinned in `requirements.txt`, so if your versions differ, run `package_model.py` again instead of loading the committed pickle. All random seeds are 42, so results repeat exactly.

The shared cleaning code lives in one place, `src/shipment_prep.py`, and is used by the training scripts and by `predict_delay.py`.

## Data findings

(From `part_a_checks.csv`, `part_a_delay_by_group.csv` and `part_a_correlations.csv`.)

The raw file had 1,224 rows. After removing 24 duplicates, 1,200 shipments remained. 278 of them were delayed, a delay rate of 0.2317.

1. **Service type:** Express is delayed most often. 119 of 243 Express parcels were late, a rate of 0.4897. Standard is 0.2056 and Economy is 0.0857.
2. **Hub tier:** delays rise as the tier number goes up: 0.0400 for Tier 1, 0.2150 for Tier 2 and 0.4400 for Tier 3.
3. **Distance:** longer distances are late far more often: 0.0219 for 0-200 km, 0.1368 for 201-400 km, 0.4364 for 401-600 km and 0.8523 for 601+ km.
4. **Strongest correlations with `delivery_hours`:** `promised_hours` 0.8372, `distance_km` 0.4013 and `n_stops` 0.3247.
5. **Why declared value was log-transformed:** the mean (INR 1,533.05) is far above the median (INR 1,121.50) because a few parcels are very expensive. After taking the log, the mean (7.0277) and median (7.0224) are almost equal, so the feature is much more balanced.

## Model results (regression)

(From `part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv` and `part_b_cv.csv`.)

- **Baseline:** always predicting the average training time gives R² = -0.0212. It explains nothing, so real models must beat it.
- **Winner on validation:** linear regression, with an RMSE of 4.8912 hours (R² 0.9313). Gradient boosting is almost tied (RMSE 4.9165).
- **Tree depth:** depth 1 is **high bias**. Train error (11.6334) and validation error (12.1324) are both high and close together, so the tree is too simple. With **no depth limit** the tree is **high variance**. Train error is 0.0 but validation error is 7.8368, so it memorised the training data. The best depth is 6, with a validation RMSE of 6.2796.
- **Learning rate:** 0.1 was best (R² 0.9306). At 0.01 (R² 0.7127) the model learns too slowly and underfits. At 1.0 (R² 0.8440) each step is too big and overshoots.
- **Cross-validation:** it ranks gradient boosting first (mean R² 0.9353) and linear regression second (0.9261), while the single validation split ranked linear regression first. Cross-validation uses five folds, so it is more reliable, and gradient boosting can also capture interactions such as sale window with Express. I would ship **gradient boosting**, though the difference is small. By the brief's rule the final tested model is linear regression, which scored R² 0.9493 and RMSE 4.5235 hours on the test set.

## Model results (classification)

(From the `part_c_*.csv` files.)

- **Blind baseline:** predicting "not delayed" for every parcel gives accuracy 0.7667, but it catches 0 of the 42 delayed parcels, so it is useless. Accuracy hides this because most parcels are on time.
- **Noise columns:** the five bookkeeping columns together take 22.4% of the forest's importance, but all five have an F-score below 10 and rank 8 to 17. So **all five are outside the top 7**. The top 7 are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag` and `sale_event_flag`.
- **Feature count (k):** validation F1 is 0.6988 for k = 5, 0.8333 for k = 7, 0.7857 for k = 10, 0.8049 for k = 12 and 0.7848 for k = 17. k = 7 is best, so it is used from here on.
- **Tuning:** grid search (135 fits) and randomized search (45 fits) did **not** beat the untuned forest on validation (F1 0.7750 and 0.7848 against 0.8333). With only 180 validation rows and 42 delayed parcels, one parcel changes F1 by about 0.02, so these differences are within noise. The untuned forest was chosen.
- **Alert threshold:** the rule is to pick the highest threshold with validation recall of at least 0.80. That is **0.5**, where validation precision is 0.7955 and recall is 0.8333. At 0.6, recall falls to 0.7619, which is too low.
- **Test result (scored once):** precision 0.6889, recall 0.7561 and F1 0.7209. Test recall is lower than validation recall (0.8333). The test set has only 41 delayed parcels, so some of the gap is chance. The threshold was picked on the validation set, so the validation numbers are somewhat optimistic.

## Operations recommendation

(From `hub_segments.csv`, `segment_profile.csv`, `tier_vs_segment_mismatch.csv`, `part_d_separation.csv`, `part_c_final_test.csv` and `new_shipment_actions.csv`.)

K-Means with K = 3 gives three segments: **Standard** (7 hubs, delay rate 0.0257), **Watch** (8 hubs, 0.1550) and **Escalate** (9 hubs, 0.4600).

- **Escalate hubs and delay rates:** Nagpur (HUB13) 0.46, Kochi (HUB15) 0.36, Patna (HUB17) 0.46, Ranchi (HUB18) 0.38, Guwahati (HUB19) 0.62, Raipur (HUB20) 0.48, Bhubaneswar (HUB21) 0.40, Siliguri (HUB23) 0.44 and Agartala (HUB24) 0.54.
- **Hubs whose tier label is misleading:** Kolkata HUB07 (Tier 1 but behaves like Watch), Nagpur HUB13 (Tier 2 but behaves like Escalate), Kochi HUB15 (Tier 2 but behaves like Escalate) and Dehradun HUB22 (Tier 3 but behaves like Watch). The tier label should not be used to pick a playbook. Use the data-based segment instead.
- **Alert threshold:** flag a parcel when its delay probability is 0.5 or higher. On the test set, precision is 0.6889, so about **7 of every 10 flagged parcels** are really delayed. Recall is 0.7561, so about **7.6 of every 10 delayed parcels** are caught.
- **New parcels:** of the 48 new parcels, **8 were flagged**. **6 of those need escalation** to the hub manager, and the other 2 get a proactive customer call.
- **Why K = 3:** the separation ratio keeps rising with K (2.8940 for K = 2, 5.3928 for K = 3, 6.3047 for K = 4 and 6.8866 for K = 5), but this happens with every extra cluster. K = 4 (sizes 8-7-5-4) and K = 5 (sizes 8-7-4-3-2) each have clusters of fewer than 6 hubs, which is too small to carry its own playbook. K = 3 (sizes 9-8-7) matches the three playbooks operations can actually run.

## Production plan

**(a) Production-readiness checklist**

| Characteristic | Where it appears in this repo |
|---|---|
| Accuracy | Test results in `part_b_metrics.csv` (R² 0.9493) and `part_c_final_test.csv` (F1 0.7209) |
| Reliability | `part_d_reload_check.csv` shows the reloaded model gives identical probabilities (difference 0.0), and stored medians fill gaps in new data |
| Reproducibility | Pinned `requirements.txt`, `random_state=42` everywhere, and a fixed run order |
| Performance (speed) | `predict_delay.py` scores the 48 new parcels in about 1.6 seconds, including Python start-up |
| Maintainability | One shared file, `src/shipment_prep.py`, and one script per Part |
| Consistency | Training and prediction use the same `clean_shipments` and `build_features`, with `impute_values.csv` and `feature_order.csv` |
| Monitorability | The monitoring quantities listed below |

**(b) What to monitor, with triggers**

1. **Weekly delayed share of delivered parcels.** The historical rate is 0.2317. Review if it is above 0.30 or below 0.16 for two weeks in a row.
2. **Weekly share of parcels flagged.** On validation about 0.24 of parcels (44 of 180) were flagged. Review if the weekly share leaves the range 0.15 to 0.35.
3. **Recall on parcels whose outcome is known.** Test recall was 0.7561. Retrain if it falls below 0.60 (using at least 40 delayed parcels).
4. **Input drift.** The median distance is 314.95 km. Review if it moves by more than 15%, or if the share of missing values in any column doubles.

**(c) Retraining and the sale window**

Retrain every month on the latest delivered parcels, and immediately if trigger 1 or 3 fires. The 15-28 September sale window should be compared with the previous sale of the same kind, not with ordinary weeks, because more delays are expected during a sale. Do not retrain on a half-finished sale. Add the full event once it ends. Data drift here would mean more long-distance parcels, a hub moving from the Watch segment to Escalate, more missing values, or the delay rate rising for the same distance and promise (for example, because of a new route or carrier).

## Limitations

1. **Synthetic data.** The data comes from a formula, so real-world results would be worse. This project proves the pipeline works, not Delhivery's real performance.
2. **Small test set.** Only 41 delayed parcels are in the test set. One parcel changes recall by about 2.4 points, so the test recall of 0.7561 is a rough estimate.
3. **Threshold tuned on one validation split.** The 0.5 threshold and the choice between three forest settings (F1 0.7750, 0.7848 and 0.8333) rest on one 180-row split, and another split could choose differently.
4. **No cost model.** The threshold follows a recall rule. Real costs in INR for calls and escalations were not available.
5. **Only 24 hubs.** The segments come from 24 hub profiles over one 90-day period, and K = 4 and K = 5 results depend on seed and hub order.
6. **Features known at dispatch.** `rain_flag` is treated as known at dispatch time, though in real life it would be a forecast. The medians for filling gaps were also computed on the full historical table.
