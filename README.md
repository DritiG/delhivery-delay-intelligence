# Delhivery Last-Mile Delay Intelligence Pipeline

Capstone project, AI & ML Certification Program, E&ICT Academy, IIT Roorkee.
One connected repository answers the three questions of the regional operations head:
**(1)** how long will a parcel really take, **(2)** which parcels will miss their promise, and
**(3)** which hubs need which playbook. All data is synthetic (produced by `generate_data.py`); Delhivery's real records are never used.

Every number quoted below is copied from a file in `outputs/` or `models/`.

## How to run

Python 3.11 or newer is needed (pandas 3.x). From a fresh clone, in this order:

```bash
pip install -r requirements.txt
python generate_data.py          # prints 24 1224 48, writes data/hubs.csv, raw_shipments.csv, new_shipments.csv
python part_a_clean_eda.py       # data/modelling_table.csv, outputs/part_a_*.csv
python part_b_regression.py      # outputs/part_b_*.csv
python part_c_classification.py  # outputs/part_c_*.csv
python part_d_segments.py        # outputs/hub_profile.csv, part_d_separation.csv, hub_segments.csv, ...
python package_model.py          # models/*, outputs/part_d_reload_check.csv
python predict_delay.py          # outputs/new_shipment_actions.csv
```

`requirements.txt` pins pandas, numpy, scikit-learn and joblib with `==`. `models/delay_model.pkl` is **regenerated by running `python package_model.py`**; a pickled model loads reliably only on the scikit-learn version pinned in `requirements.txt` (1.8.0), so on a machine with different versions re-run `package_model.py` instead of loading the committed pickle. Every script is deterministic (all `random_state` values are 42 as the brief requires), and `predict_delay.py` produces byte-identical output on repeated runs.

Repository layout: `src/shipment_prep.py` holds the shared constants (`PROMISED_HOURS`, `FEATURES`, `NOISE_COLUMNS`) and the two shared functions `clean_shipments` and `build_features`, which are used by Part A, `package_model.py` and `predict_delay.py` (there is only one copy of the cleaning logic).

## Data findings

Source: `outputs/part_a_checks.csv`, `part_a_delay_by_group.csv`, `part_a_correlations.csv`.

The raw export has 1,224 rows; 24 exact duplicates were removed, leaving 1,200 shipments. 5 weight values of 999.0 were scanner-fault sentinels and were treated as missing. The 12 service-type spellings were reduced to 3. After cleaning, the 17 feature columns, `delivery_hours` and `is_delayed` contain 0 missing cells. 278 parcels (delay rate 0.2317) missed their promise.

1. **Service type.** Express parcels are delayed most often: 119 of 243, a delay rate of 0.4897. Standard is 0.2056 and Economy 0.0857.
2. **Hub tier.** The delay rate climbs steeply with tier: 0.0400 (Tier 1) to 0.2150 (Tier 2) to 0.4400 (Tier 3).
3. **Distance.** The delay rate rises sharply with lane distance: 0.0219 (0-200 km), 0.1368 (201-400 km), 0.4364 (401-600 km) and 0.8523 (601+ km, 75 of 88 parcels).
4. **Strongest correlations with `delivery_hours`** (ranked by absolute value, excluding itself): `promised_hours` 0.8372, `distance_km` 0.4013, `n_stops` 0.3247.
5. **Why `declared_value_inr` was log-transformed.** On the median-filled column the mean is INR 1,533.05 against a median of INR 1,121.50 (right-skewed, long tail of expensive parcels), whereas after the natural log the mean (7.0277) and median (7.0224) almost coincide, giving a near-symmetric feature.

The IQR rule on `delivery_hours` (bounds -0.7063 and 116.5238) flags only 1 outlier, so no rows were dropped.

## Model results (regression)

Source: `outputs/part_b_checks.csv`, `part_b_metrics.csv`, `part_b_tree_depth.csv`, `part_b_gb_learning_rate.csv`, `part_b_cv.csv`.

The split is 840 / 180 / 180. The scaler was fitted on the 840 training rows only: the largest absolute column mean is 0.0 on the training rows (about 4e-16 before rounding) but 0.2187 on the test rows, which confirms nothing leaked from the test set.

- **Baseline.** Predicting the training mean for every validation parcel gives R² = -0.0212 (RMSE 18.8552 hours). It explains none of the variation, so every real model must be judged against it.
- **Winner on validation.** Linear regression, RMSE 4.8912 hours (R² 0.9313). Gradient boosting is practically tied (RMSE 4.9165, R² 0.9306), then random forest (5.5095, 0.9128) and the decision tree (6.2796, 0.8867).
- **Tree depth.** Depth 1 is **high bias**: train RMSE 11.6334 and validation RMSE 12.1324 are both high and close (gap 0.4990), so the tree is too simple. With no depth limit the tree is **high variance**: train RMSE 0.0 but validation RMSE 7.8368 (gap 7.8368), i.e. it memorises the training rows; depth 12 shows the same pattern (train 1.3613, validation 7.3540). The best depth is 6 (validation RMSE 6.2796); beyond it the validation error rises again while the training error keeps falling.
- **Learning rate.** 0.1 was best (validation R² 0.9306, RMSE 4.9165). At 0.01 (R² 0.7127) the 100 trees each move the prediction only 1% of the way, so the ensemble is still far from the target (too slow, under-fitted). At 1.0 (R² 0.8440) every tree takes a full step and over-corrects the errors of the previous ones, so the fit overshoots and chases noise.
- **Cross-validation disagrees slightly with the validation ranking.** On the 1,020 train+validation rows with one shared 5-fold `KFold`, gradient boosting scores a mean R² of 0.9353 (std 0.0045) and linear regression 0.9261 (std 0.0048). Validation, a single 180-row slice, ranked linear regression first by only 0.0253 hours of RMSE, whereas cross-validation averages five folds and is the steadier estimate. I would therefore ship **gradient boosting**: it wins the more reliable comparison and can represent the interactions in the data (sale window × Express, long distance × rain) that a linear model cannot. The gap is small, so linear regression remains a good, interpretable fallback. Following the brief's protocol, the final model (lowest validation RMSE) is linear regression, scored once on the test rows: RMSE 4.5235 hours, R² 0.9493. Gradient boosting has no test score because the test set may be used only once.

## Model results (classification)

Source: `outputs/part_c_*.csv`. Split: 840 / 180 / 180 rows with 195 / 42 / 41 delayed parcels.

- **Blind baseline.** Predicting "not delayed" for everything reaches accuracy 0.7667 (TN 138, FN 42, TP 0), but it has recall 0.0 and catches no delayed parcel, so it is useless for operations; accuracy alone hides this because 77% of parcels are on time. The trained models reach 0.8833 to 0.9056 validation accuracy: logistic regression F1 0.8046, decision tree (depth 6) F1 0.7470, default random forest F1 0.7848.
- **Noise columns.** The five bookkeeping columns together hold 22.4% of the forest's importance (sum of `rf_importance` over `is_noise` rows in `part_c_feature_scores.csv`, about 0.224) even though they carry no signal, because a deep forest can split on any column. By F-score they are clearly separated: all five have an F-score below 10 (the largest is 4.5847) and rank 8 to 17, so **all five fall outside the top 7**. The top 7 by F-score are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag`, `sale_event_flag` (the smallest F-score among them is 36.7281).
- **Select-k table.** Validation F1 with k = 5, 7, 10, 12, 17 is 0.6988, 0.8333, 0.7857, 0.8049, 0.7848. k = 7, exactly the columns with real signal, is best; k = 5 drops useful features and hurts, while keeping the noise columns (k = 17) gives no gain. k = 7 is used from here on.
- **Tuning.** Grid search (27 candidates × 5 folds = 135 fits) reached a best CV accuracy of 0.8952 and randomized search (9 × 5 = 45 fits) 0.8905, but their validation F1 (0.7750 and 0.7848) did **not** beat the untuned forest on the same 7 columns (0.8333). A 180-row validation set with only 42 delayed parcels is too small to separate such close candidates: one parcel moves F1 by roughly 0.02, so the differences are within noise. The untuned forest was kept because the rule says highest validation F1, not because tuning is proven useless. Final configuration: `SelectKBest(k=7)` + forest with n_estimators 100, no depth limit, min_samples_leaf 1.
- **Alert threshold.** Validation recall is 0.9762 at 0.1, 0.9286 at 0.2 and 0.3, 0.8810 at 0.4, 0.8333 at 0.5 and drops to 0.7619 at 0.6. The operations rule (highest threshold with recall ≥ 0.80) therefore gives **0.5**, where validation precision is 0.7955 and recall 0.8333 (TP 35, FP 9, FN 7). Raising it to 0.6 would lift precision to 0.8889 but miss more delayed parcels (recall 0.7619), which the cost rule does not accept.
- **Test result (scored once, threshold 0.5).** Precision 0.6889, recall 0.7561, F1 0.7209, accuracy 0.8667 (TP 31, FP 14, FN 10). Test recall is lower than validation recall (0.7561 vs 0.8333). With only 41 delayed test parcels, missing 10 instead of 7 is a difference of about three parcels, so some of the gap is chance; but the honest reading is that the threshold was picked on the validation set, so the validation numbers are optimistic and about three in four delayed parcels (not four in five) is the realistic catch rate.

## Operations recommendation

Source: `outputs/hub_segments.csv`, `segment_profile.csv`, `tier_vs_segment_mismatch.csv`, `part_d_separation.csv`, `part_c_final_test.csv`, `new_shipment_actions.csv`.

K-Means (K = 3) on the scaled hub profiles gives three playbooks: **Standard** (7 hubs, delay rate 0.0257), **Watch** (8 hubs, 0.1550) and **Escalate** (9 hubs, 0.4600).

- **Escalate hubs and their delay rates:** Nagpur (HUB13) 0.46, Kochi (HUB15) 0.36, Patna (HUB17) 0.46, Ranchi (HUB18) 0.38, Guwahati (HUB19) 0.62, Raipur (HUB20) 0.48, Bhubaneswar (HUB21) 0.40, Siliguri (HUB23) 0.44 and Agartala (HUB24) 0.54. They have the longest lanes (mean 470.4757 km) and routes (mean 84.3444 stops).
- **Hubs whose tier label is misleading** (`tier_vs_segment_mismatch.csv`): **Kolkata HUB07** (Tier 1, behaves like Watch), **Nagpur HUB13** (Tier 2, behaves like Escalate), **Kochi HUB15** (Tier 2, behaves like Escalate) and **Dehradun HUB22** (Tier 3, behaves like Watch). The tier label must not be used to choose a playbook: Nagpur and Kochi need escalation although labelled Tier 2, and Kolkata and Dehradun do not fit their Tier 1 and Tier 3 labels. Use the data-driven segment, and refresh it regularly.
- **Alert threshold and its reliability.** Flag a parcel when its delay probability is at least **0.5**. On the test rows, precision is 0.6889, so about **7 of every 10 flagged parcels are really delayed**, and recall is 0.7561, so about **7.6 of every 10 delayed parcels are caught** (roughly 3 in 4).
- **New parcels.** Of the 48 new parcels, **8 were flagged** and **6 of those need an escalation to the hub manager** (they are in Escalate hubs); the other 2 get a proactive customer call (Watch hubs). 40 parcels need no action.
- **Why K = 3.** The across/within ratio rises with K (2.8940 for K = 2, 5.3928 for K = 3, 6.3047 for K = 4, 6.8866 for K = 5), but it rises mechanically with every extra cluster. K = 4 (sizes 8-7-5-4) and K = 5 (sizes 8-7-4-3-2) both contain clusters of fewer than 6 hubs, too small to carry their own playbook, whereas K = 3 (9-8-7) matches the three playbooks operations can run and gives a big jump over K = 2.

## Production plan

**(a) Production-readiness characteristics mapped to the repository**

| Characteristic | Item in this repository |
|---|---|
| Accuracy | Held-out test results in `part_b_metrics.csv` (R² 0.9493) and `part_c_final_test.csv` (F1 0.7209); validation used for all choices |
| Reliability | `part_d_reload_check.csv` proves the saved pickle reloads with probability difference 0.0; the scoring script never fails on gaps because it uses stored medians |
| Reproducibility | Pinned `requirements.txt`, fixed `random_state=42`, committed generator, run order in this README, byte-identical `new_shipment_actions.csv` on re-runs |
| Performance (speed) | `predict_delay.py` cleans and scores the 48 new parcels in about 1.6 seconds including Python start-up (measured), and the whole pipeline re-runs in about 35 seconds; no network or paid service is needed |
| Maintainability | One shared module `src/shipment_prep.py`, one script per Part, constants defined once |
| Consistency | `predict_delay.py` calls the same `clean_shipments` and `build_features` used in training, with stored medians (`impute_values.csv`) and the stored column order (`feature_order.csv`) |
| Monitorability | The monitoring quantities below, each computable from `new_shipment_actions.csv` plus delivered outcomes |

**(b) What to monitor, with triggers**

1. **Weekly delayed share of delivered parcels.** The historical rate is 0.2317. Trigger a review if it is above 0.30 or below 0.16 for two weeks in a row.
2. **Weekly share of parcels flagged.** On validation 44 of 180 parcels (about 0.24) were flagged at threshold 0.5. Trigger if the weekly share leaves 0.15 to 0.35.
3. **Recall on parcels whose outcome is now known** (rolling window with at least 40 delayed parcels). Test recall was 0.7561. Trigger retraining if it falls below 0.60.
4. **Input drift:** the median `distance_km` (historical 314.95 km) and the share of missing values per column; trigger if the median moves by more than 15% or the missing share of any column doubles.

**(c) Retraining and the sale window.** Retrain monthly on the most recent delivered parcels, and immediately if trigger 1 or 3 fires. The 15-28 September sale window (`sale_event_flag`) must be judged against the same kind of event (last sale), not against ordinary weeks; a higher delay rate and flag share during the sale is expected, as the window is in the data once. Do not retrain on a half-finished sale; add the complete event after it ends so the model learns it. Data drift here would look like a changed lane mix (more long-distance parcels), a change in the tier/segment structure (a hub drifting from Watch to Escalate), more missing values, or concept drift, where the delay rate at the same distance and promise rises (for example because of a new carrier or route).

## Limitations

1. **Synthetic data.** Every row comes from a generator with known formulas, so real-world performance (messier causes, unseen lanes) will be lower, and the results prove the pipeline, not Delhivery's actual performance.
2. **Small test set.** Only 41 delayed parcels are in the test set; one parcel changes recall by about 2.4 points, so the test recall of 0.7561 is a noisy estimate.
3. **Threshold and configuration tuned on one validation split.** The 0.5 threshold and the choice between three forest configurations (validation F1 0.7750, 0.7848, 0.8333) rest on a single 180-row split with 42 delayed parcels; a different split could pick a different threshold.
4. **Recall rule, not a cost model.** The threshold follows the "recall at least 0.80" rule; real costs of calls and escalations in INR were not available, so the best threshold in money terms is unknown.
5. **Segments rest on 24 hubs.** K-Means on 24 hub profiles of 50 parcels each is sensitive to the hub order and seed for K = 4 and 5, and the profiles are only a snapshot of one 90-day period.
6. **Features known at dispatch.** `rain_flag` and `sale_event_flag` are treated as known at dispatch time (in practice the first would be a forecast), and the medians used to fill gaps were computed on the full historical table.
